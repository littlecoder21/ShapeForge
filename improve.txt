# ShapeForge — Unified Mesh Gradient to Procedural WebGL Integration

## Objective

Upgrade ShapeForge so the existing Mesh Gradient system can render through the Procedural WebGL engine using the exact same mesh points, controls, and project data.

Currently, the CSS mesh renderer generates multiple radial gradients, one for each mesh point, and combines them into a single CSS background.

I want to add a procedural rendering backend that evaluates all mesh points inside a single WebGL fragment shader and produces the complete mesh gradient as one rendered output.

**Do not rebuild the mesh editor. Do not replace the existing CSS renderer. Extend the current architecture and reuse existing systems wherever possible.**

The result should allow users to switch between CSS Mesh Rendering and Procedural WebGL Rendering without recreating their mesh.

# 2. Add Two Mesh Rendering Modes

Create two rendering modes using the same mesh data.

### Mode A: CSS-Compatible Mesh

Keep the current CSS implementation unchanged as the default rendering mode.

It should continue generating radial-gradient background images as it currently does.

### Mode B: Procedural WebGL Mesh

Add a procedural rendering backend that converts the existing mesh points into shader uniforms and renders the complete mesh in one WebGL rendering pass.

The output should be one rendered surface rather than multiple independently rendered CSS gradient images.

The user should be able to switch between both modes without losing settings.

Suggested architecture:

    |

# 3. Implement CSS-Compatible Shader Rendering

This is the most important requirement.

The current CSS implementation uses multiple transparent radial gradients.

The procedural renderer must have a mode that closely reproduces the existing CSS output.

Inspect the actual implementation in `mesh.ts` and reproduce its behavior, including:

- Radial gradient dimensions
- Elliptical radius calculations
- Aspect-ratio correction
- Point positions
- Point colors
- Point alpha
- Core/middle stop behavior
- Transparent outer falloff
- Layer opacity
- Mesh base color
- Gradient stop interpolation
- Point compositing order

Do not replace this with a completely different interpolation algorithm and call it equivalent.

### Alpha compositing

Implement the equivalent of CSS background-image compositing inside the fragment shader.

Each point should calculate its radial color and alpha contribution.

Then combine the contributions using source-over alpha compositing in the correct order.

Important:

CSS background images have a stacking order. Verify the actual order used by the current CSS renderer and reproduce it correctly in the shader.

Use correct premultiplied-alpha mathematics where necessary.

Do not simply average the colors of all points.

### Radial falloff

Reproduce the current CSS radial-gradient behavior as closely as possible.

Use the existing point radius calculations and core-stop logic rather than inventing new values.

For example, the current mesh implementation derives the middle stop from the point's core value. Preserve the same mapping.

Make the radial evaluation support elliptical gradients, not just circular distance.

### Color accuracy

Pay special attention to:

- sRGB versus linear color space
- Premultiplied versus straight alpha
- Color interpolation
- Alpha interpolation
- Browser CSS gradient behavior

The goal is to make the WebGL output visually as close as possible to the existing CSS output.

Do not claim pixel-perfect equivalence unless it has been verified through actual comparisons.

# 4. Add Unified Mesh Field Rendering

In addition to CSS-compatible rendering, implement a second shader algorithm called Unified Mesh Field.

This should not be confused with CSS-compatible rendering.

It should create a mathematically unified color field where all mesh points influence one continuous surface.

The goal is to produce smoother, more organic and more continuous color transitions than stacked radial gradients.

Support multiple field algorithms:

- Gaussian
- Inverse Distance Weighting (IDW)
- Smooth interpolation
- Radial influence
- Soft field
- Smooth minimum where appropriate

Each algorithm should use the same mesh point positions, colors, alpha, and size values.

Add appropriate falloff and normalization to prevent unwanted dark areas, washed-out colors, and unstable transitions.

The field should account for the mesh canvas aspect ratio.

Do not remove or alter the CSS-compatible mode when introducing these algorithms.

### Recommended initial Gaussian model

Use this as a starting point, not as a fixed final implementation:

```glsl
vec3 colorSum = vec3(0.0);
float weightSum = 0.0;

for (int i = 0; i < POINT_COUNT; i++) {
    vec2 delta = uv - uPointPosition[i];

    float distanceFromPoint = length(
        delta * uAspectCorrection
    );

    float radius = max(uPointRadius[i], 0.0001);

    float normalizedDistance = distanceFromPoint / radius;

    float weight = exp(
        -normalizedDistance * normalizedDistance * 3.0
    );

    weight *= uPointAlpha[i];

    colorSum += uPointColor[i] * weight;
    weightSum += weight;
}

vec3 finalColor = colorSum / max(weightSum, 0.0001);
```

Improve the formula where needed.

The final algorithm must preserve the intended influence of each point and avoid numerical instability.

# 6. Handle the Point Count Limit Correctly

Inspect the existing procedural engine before implementing the mesh adapter.

The current procedural system has a `PROC_MAX_POINTS` limit of 12, while the mesh system may support significantly more points.

Do not silently truncate mesh points.

Design a proper point-capacity strategy.

Consider:

1. Dynamically generated shader loop sizes.
2. Uniform arrays with an appropriate capacity.
3. Texture-based point data when supported and useful.
4. WebGL2 uniform buffers or other suitable data storage.
5. Batching only as a fallback when necessary.

The system must respect hardware limits.

Query the relevant GPU capabilities and select a supported strategy.

Do not assume every device supports the same maximum number of points.

If the user exceeds the supported capacity:

- Provide a clear warning.
- Preserve all mesh data.
- Never silently delete or overwrite points.
- Offer a quality/performance fallback.
- Make sure the CSS renderer still supports the full mesh.

The procedural renderer should support the largest practical point count without causing unnecessary shader recompilation.

# 10. Shared WebGL Renderer and Performance

The procedural mesh renderer must use the existing shared WebGL renderer.

Do not create one WebGL context per mesh point.

Do not create one renderer per gradient point.

Do not create an independent animation loop for every mesh layer.

Use the existing shared renderer and resource management architecture.

Optimize the mesh renderer for multiple procedural mesh layers.

Important performance requirements:

- Reuse shader programs.
- Reuse buffers and textures.
- Avoid unnecessary shader recompilation.
- Update only changed uniforms.
- Avoid rebuilding point arrays when only one point changes.
- Avoid unnecessary GPU uploads.
- Skip invisible or disabled layers.
- Pause animation when appropriate.
- Avoid rendering when nothing changes and animation is disabled.
- Use adaptive resolution where appropriate.
- Support quality settings.
- Clean up resources correctly when layers are removed.

Make sure adding multiple procedural mesh layers does not create a separate WebGL context or separate animation scheduler for every layer.

Preserve independent settings and state for each layer.

# Final Acceptance Criteria

The implementation is complete only when:

1. Existing CSS mesh gradients work exactly as before.
2. The same mesh editor controls both renderers.
3. CSS and procedural rendering use the same source mesh data.
4. Procedural CSS-Compatible mode closely reproduces the current CSS appearance.
5. All points are composited inside one fragment shader output.
6. Unified Field mode provides a genuinely continuous procedural color field.
7. Existing procedural distortion, animation, and interaction systems can be reused.
8. Multiple procedural mesh layers use the existing shared WebGL renderer.
9. Point limits are handled safely without silently losing mesh data.
10. Switching rendering modes does not destroy or reset mesh settings.
11. Save/load and undo/redo continue working.
12. Existing projects and unrelated gradient features remain functional.

**Final instruction:** Prioritize visual correctness and architectural integration over adding many new controls. First make the existing mesh render correctly in one WebGL output. Then progressively enable the advanced procedural capabilities. Do not sacrifice the current CSS implementation to achieve this.
