# MASTER ENGINEERING PROMPT — Build 8 Advanced Visual-Effect Builders in My Existing Gradient & Shape Studio

## 1. Project Context

I have an existing web-based Shape & Gradient Generator built with React, TypeScript, and an established rendering architecture.

The project already includes multiple gradient builders, shared rendering utilities, reusable layer structures, color conversion functions, seeded randomness, and existing UI patterns.

Examples of existing concepts and utilities include:

- `GradientLayer[]`
- `newLayer()`
- `newEffect()`
- `hslToHex()`
- `mulberry()` seeded randomness
- Color stops, layer transforms, and effect configuration
- Existing gradient and atmosphere rendering systems

These are examples from my project, not permission to assume every utility has the same implementation or API.

**Your first responsibility is to inspect the actual codebase before changing anything.**

Understand the existing architecture, component conventions, rendering pipeline, state management, export mechanisms, styling system, and performance constraints.

Do not invent existing APIs. Adapt your implementation to the actual source code.

## 2. Main Objective

Build eight powerful, production-quality visual-effect builders that integrate into my existing application.

Implement these builders:

1. Fluid Builder
2. Light Builder

1. Inspect the repository and map its architecture.

## 14. Rendering Technology Strategy

Choose the rendering technology based on the actual requirements and the existing project.

Prefer lightweight Canvas 2D or CSS when they provide sufficient quality.

Use SVG for vector-friendly patterns, masks, and scalable effects.

Consider WebGL or an existing GPU framework only when its benefits justify the additional complexity.

Do not introduce a new rendering framework simply because it is available.

For each builder, determine:

- Whether its output should be vector-based, raster-based, or hybrid
- Whether live animation is necessary
- Whether it requires image sampling
- Whether GPU acceleration materially improves performance
- Whether its output can be exported as CSS, SVG, PNG, or a combination

Never pretend that an effect is natively editable CSS if it actually requires a raster image.

## 15. Performance Requirements

Performance is a core feature, not a final cleanup task.

Implement appropriate safeguards:

- Device-pixel-ratio-aware rendering
- Configurable preview resolution
- Full-resolution export independent of preview quality
- Animation through `requestAnimationFrame`
- Avoid unnecessary React rerenders during animation
- Cancel animation frames when no longer needed
- Clean up observers, event listeners, and rendering resources
- Debounce expensive non-interactive operations where appropriate
- Avoid rebuilding static textures on every frame
- Cache reusable gradients, patterns, and noise fields
- Avoid repeated canvas allocations
- Handle resizing without distorting the artwork
- Respect reduced-motion preferences where relevant
- Use workers for genuinely expensive CPU work when justified
- Avoid unbounded particle counts and texture resolutions
- Provide quality levels such as Draft, Balanced, and High where useful

Ensure controls remain responsive while users change settings.

If a builder supports animation, include a clear pause/play control and deterministic seed behavior.

## 17. Presets and Randomization

Each builder must have at least six high-quality, visually distinct presets.

Presets should represent useful design outcomes rather than merely changing one color.

A preset should configure all relevant parameters together.

Provide controlled randomization that respects valid parameter ranges and produces visually coherent results.

Where supported, expose a seed field and a regenerate action.

Use a deterministic random generator for repeatable procedural results. Do not make randomization depend on uncontrolled `Math.random()` calls throughout the rendering loop.

## 18. Export System

Integrate exports into the existing project's export architecture.

Provide the appropriate options for each builder:

- PNG for raster artwork
- SVG for genuinely vector-based effects
- CSS for effects that can be represented faithfully using CSS
- CSS background layers when supported
- Transparent PNG when the effect supports transparency
- High-resolution export
- Configuration serialization for saving and restoring work

Do not generate fake SVG containing only a raster image and describe it as fully editable vector output.

Do not export an approximate CSS version without communicating its limitations.

When a builder produces procedural pixels, PNG may be its most faithful export.

Preserve transparent backgrounds when requested and avoid unintended background fills.

Ensure export resolution is independent of the current preview resolution.

## 20. Implementation Strategy

Do not attempt a massive unverified rewrite.

Work in these phases:

### Phase A — Audit

Inspect the repository and document the current architecture, reusable utilities, integration points, and risks.

### Phase B — Shared Infrastructure

Implement only the shared interfaces, helpers, and export integration genuinely needed by the new builders.

### Phase C — Builder Implementation

Implement the eight builders in manageable increments. Prefer completing one builder's rendering, controls, presets, integration, and tests before proceeding to the next.

Prioritize architectural validation with representative builders that use different rendering approaches. Reuse the validated infrastructure without forcing all builders into identical rendering methods.

### Phase D — Integration

Register every builder in the existing navigation and connect it to the existing state and preview systems.

### Phase E — Verification

Run the available checks and fix regressions before declaring the work complete.

Summarize:

- Files created

- Implemented features for each builder
- Rendering technology used by each builder
